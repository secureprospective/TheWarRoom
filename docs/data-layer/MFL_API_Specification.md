# Legacy NFL — MFL API Data Layer Specification
Version: 1.0 — June 2026
Status: Reference document. Pipeline build is a separate session.

## Overview
MyFantasyLeague (MFL) provides a free, public developer API. This is the primary data source for all 32 team rosters, contracts, scoring, standings, and transaction history. No manual exports required.

The application reads from MFL via the API. MFL remains the official league record. The application adds the valuation intelligence layer MFL does not provide.

## API Base URL
```
https://api.myfantasyleague.com/{year}/export?TYPE={endpoint}&L={league_id}&JSON=1
```

- `{year}` — current season year (e.g., 2026)
- `{endpoint}` — the data type requested (see below)
- `{league_id}` — the Legacy NFL league ID on MFL
- `JSON=1` — returns JSON instead of XML (always use JSON)

Developer portal: `https://api.myfantasyleague.com/{year}/api_info`

## Key Technical Rules

- Player IDs are 4-5 digit strings, not integers. IDs under 1000 require a leading zero (e.g., "0531" not "531"). Always treat as strings.
- The player database updates once per day. Cache it. Do not request more than once per day.
- Live scoring and schedule data updates in real time during games.
- Weekly results and player scores update after preliminary and final results (a few hours after games).
- API returns 429 status if rate limited. Do not retry on failure — back off and wait.
- All calls must be made server-side. Cross-domain JavaScript from outside myfantasyleague.com is blocked.
- Use https://api.myfantasyleague.com as the host for non-league-specific requests — this spreads load across servers.

## Write Access Status
The MFL API is primarily read-only. Write operations (lineup submission, waiver claims, trade processing) exist but require authenticated user credentials — not just a league ID. MFL explicitly forbids making changes to a league or team without the owner's permission.

### Build Strategy for Write Operations
- **Phase 1 (Current):** Application operates as read + intelligence layer. Transaction outputs (winning bids, waiver claims, trade formats) are generated by the application and executed manually by the GM on MFL.
- **Phase 2 (Future):** Authenticated user login flow. Each GM authenticates through MFL with their own credentials. Application submits transactions on their behalf with explicit user permission.
- **Phase 3 (Long-term):** Computer-use / screen-interaction layer. Click-through automation on the MFL interface. Codex-style execution. Scope noted — not a near-term build target.

## Data Pipeline Architecture (Phase 1 Design)

```
MFL API
    ↓
Data Ingestion Layer
    - Fetch all 32 rosters
    - Fetch all contracts
    - Fetch player database
    - Fetch weekly scoring
    - Cache daily data appropriately
    ↓
Data Normalization Layer
    - Map EDGE → DE or LB (positional mapping)
    - Enforce string type on player IDs
    - Validate salary against rulebook minimums
    - Flag missing RAS / fill with position group mean
    - Append external data (RAS from ras.football, age from NFL.com)
    ↓
Scoring Engine
    - Layer 1: Data hygiene
    - Layer 2: Scoring matrix
    - Layer 3: Age decay
    - Layer 4: Scouting layer
    - Layer 5: Cap efficiency scaling
    - Layer 6: Tiebreaker resolution
    ↓
Output Layer
    - 32-team asset rankings
    - Individual team views
    - Power rankings
    - Matchup projections
    - Transaction intelligence
```

## Known Data Risks

- **EDGE Classification:** MFL may classify some players as EDGE. The True Position split in the scoring engine requires explicit DE or LB. Mapping logic must resolve this before the scoring layer runs.
- **Practice Squad Eligibility:** The rulebook uses NFL.com career games played to track experience for practice squad eligibility. This data must be pulled from NFL.com, not MFL, as MFL tracks legacy experience differently.
- **Salary Adjustments:** The Arizona Cardinals MFL export showed a $5.49 salary adjustment line item. The API must account for these adjustments in cap calculations — raw salary sum may not equal cap usage.
- **Player ID Consistency:** MFL player IDs are stable within MFL but do not map directly to NFL.com or PFF player IDs. A cross-reference table will be needed once external data sources are integrated.
