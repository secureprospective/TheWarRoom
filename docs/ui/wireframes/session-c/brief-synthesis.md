## HEAD-BRAIN RULINGS — implement these, do not reopen
1. **BASE = the cold CIC direction (Run 2), NOT warm.** A dynasty command console wants disciplined cold depth; warm anthracite drifts toward sepia and (Run 1 itself confessed) fights amber legibility — and amber is the most important escalation color in an app full of bid clocks. Keep Run 2's cold desaturated-navy base family (`--surface-canvas` ≈ `hsl(220, 20%, 6%)` and its sunken/tile/overlay ramp). Commit the full `--surface-*` ramp + the inset-bevel highlight/shadow tokens the Session-A actuation language needs.
2. **SEMANTIC RAMPS = Run 1's disciplined mid-saturation values, NOT Run 2's loud phosphor.** Run 2's `#00FF9D` elite green is too loud for a 500-row board where dozens of cells are green (its own restraint section warns of exactly this Christmas-tree risk). Use Run 1's controlled ramp saturations. BUT keep them legible on the COLD base (re-check contrast — Run 1's values were tuned for a warm ground; nudge lightness/hue as needed and state that you did).
3. **SCORE→HUE BANDING = Run 1's explicit ramp, verbatim in structure:** Adjusted Score ≥90 → green-loud, 80–89 → green-base, 70–79 → blue-base, 55–69 → amber-base, <55 → red-base. This is the buildable mapping; keep it.
4. **FRESHNESS = COMPOSE both.** Take Run 2's three-state EDGE grammar (live = 1px blue edge / stale-cache = amber edge / failed-refresh = 2px RED edge + timestamp text recolors + `(cache)`/`(offline)` suffix) AND Run 1's guardrail on top ("never wash out the DATA — the numbers stay fully colored/legible; only the freshness chrome + timestamp change"). Both compose; deliver `--freshness-*` accordingly, consistent across every surface, reinforcing Session B's cache-only state-line.
5. **POSITION BADGES = Run 2's style** (sunken bg + 1px colored border + colored text), which also doubles as the casual-relief valve. Resolve categorical-vs-semantic: badge hues must NOT collide with the 5 semantic meanings — pick categorical hues (or a treatment) that reads as "category label," not "signal." State the rule.
6. **FOCUS RING = BLUE, not amber.** Amber is a semantic (watch/warning); using it for keyboard focus pollutes the signal. Keyboard focus = 1px blue inset ring (machined, no glow). Lock it.
7. **SELECTION ≠ a value judgment.** Both runs put GREEN on the 2px left-axis selection border — but green means elite/positive, and selecting a row is not a positive verdict on it. Rule: selection border = a NEUTRAL bright edge (a bright gray/`--text`-derived tone) OR blue — NOT green. Keep green reserved for score meaning. Pick one and state it.
8. **RESTRAINT DOCTRINE is the spine — make it loud and explicit.** Color belongs to DATA (scores, deltas, clocks) and STATE (focus, active, hold-to-fire fill, freshness) ONLY. Row/tile/canvas backgrounds are permanently achromatic `--surface-*` — NEVER tint a row background by delta. Hover/select are optical (surface + bevel), not chromatic. UI chrome icons/sort arrows are `--text-*`, never semantic. Matrix density: all semantic hue yields to `--text-primary` EXCEPT red-danger; hierarchy rides delta-in-weight. State the one rule that keeps a 500-row board from lighting up.
9. **MOTION DOCTRINE** unchanged from both runs (they agreed): transforms/opacity only, ≤150ms, feedback-only, Matrix kills all motion (`--motion-multiplier: 0` / `transition: none`). Keep the four named cases (feed arrival translate+fade, hold-to-fire scaleX fill, engine-reject red opacity flash, clock<1hr amber timestamp shift). Give each a named duration.
